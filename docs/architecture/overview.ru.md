# Обзор архитектуры

Unison - это набор процессов, у которых одно общее ядро на Go:

| Процесс | Бинарник | С кем взаимодействует |
|---------|----------|----------|
| Демон | `unisond` | с пирами по QUIC, с десктопным приложением и CLI по локальному API |
| Десктопное приложение | сборка Tauri | с демоном по локальному API |
| Android-приложение | APK с ядром в виде AAR | с ядром в том же процессе |
| Relay | `unison-relay` | с устройствами по QUIC и WebSocket, больше ни с чем |

Демон - это и есть устройство. Он владеет идентичностью, базой данных, конвейером буфера обмена и
соединениями с пирами. Все, что видит пользователь, - клиент демона, кроме Android, где ядро
работает внутри процесса приложения и UI вызывает его напрямую.

```
desktop app (Tauri + Svelte)   CLI (unison)        Android app (Kotlin)
            \                     /                        |
             +--- local API -----+                         | in process
                        |                                   |
                  +-----------+                    +-------------------+
                  |  unisond  |                    |  core (Go, AAR)   |
                  +-----------+                    +-------------------+
                        |
             QUIC, TLS, mDNS, relay
                        |
                  other devices
```

## Слои

Репозиторий разделен по слоям, и зависимости идут только вниз:

| Слой | Пути | Роль |
|-------|-------|------|
| Точки входа | `cmd/`, `mobile/`, `desktop/`, `android/app` | запускают процесс и связывают ядро |
| Композиция | `core/node` | собирает домены в работающее устройство |
| Домены | `core/*` | доверие, спаривание, обнаружение, буфер обмена, blob-хранилище, история, отправка файлов, relay |
| Протокол | `core/session`, `core/transport`, `proto/` | кадры, потоки, возможности в сети |
| Порты | `core/ports` | хранилище ключей, буфер обмена, обнаружение, часы |
| Платформа | `platform/darwin`, `platform/windows` | порты для реальной ОС |
| Общая инфраструктура | `core/store`, `core/model`, `core/api`, `internal/` | хранилище, типы, локальный API, помощники демона |

`core/node` - единственный пакет, который собирает домены. Домен знает свое хранилище, свои
сообщения протокола и свои лимиты, а до других доменов достает через интерфейсы, которые передает
узел, а не через их импорт.

## Идентичность устройства

При первом запуске создается пара ключей Ed25519 и ML-DSA-65. ID устройства выводится из обоих
публичных ключей. Семена лежат в хранилище ключей платформы, идентичность подписывает
доказательство сессии и записи группы, и больше в системе нет корня доверия: нет аккаунта и нет
сервиса, которому устройство обязано доверять.

Спаренное устройство - это запись с публичными ключами, именем, платформой, ролью и временем
последней доступности. Ролей две:

- **Personal** - устройства одного человека, с общим ключом обнаружения, общей историей и
  записью группы, которая распространяет представления и отзывы.
- **Friends** - устройства других людей, спаренные один на один, без ключа группы.

Роль проверяется на каждом сообщении и каждом потоке матрицей возможностей сессии, поэтому
устройство Friends не может прочитать историю, даже если попросит.

## Связность

Устройство слушает QUIC-сокет с mutual TLS, гибридным пост-квантовым обменом ключами и ALPN
`unison/1`. Адреса берутся из обнаружения mDNS, из кеша адресов пира, из ручного адреса и из
relay. Два спаренных устройства держат ровно одно соединение: одновременный дозвон разрешается
сравнением ID устройств.

Relay необязателен. Он пересылает непрозрачные датаграммы между участниками почтового ящика, так
что пиры по-прежнему проводят свое QUIC-соединение сквозным образом; relay не видит ни ключей, ни
открытого текста. Локальная сеть всегда выигрывает: путь через relay открывается, только когда
пир остается недоступным напрямую.

## Данные

Один каталог данных на экземпляр устройства содержит все:

| Содержимое | Где |
|---------|-------|
| База SQLite | `<data dir>/unison.db` |
| Blob-хранилище | `<data dir>/blobs` |
| Логи | `<data dir>/logs/unisond.log` |
| Блокировка | `<data dir>/unisond.lock` |
| Эндпоинт локального API | `<data dir>/unisond.sock` (macOS), производный named pipe (Windows) |
| Секреты | хранилище ключей платформы, никогда в каталоге |

Чувствительные значения базы и каждый чанк blob запечатаны ключом шифрования данных, который
лежит в хранилище ключей, поэтому копию каталога без ключа прочитать нельзя. Каждый домен держит
свои миграции и свои таблицы в одном файле SQLite.

## Границы доверия

- Сеть: все, что приходит от пира, аутентифицируется через TLS, а затем фильтруется матрицей
  ролей и лимитами размера и частоты сессии.
- Локальный эндпоинт: unix-сокет в каталоге, куда может войти только пользователь, или named pipe
  с дескриптором для текущего пользователя. Клиент отказывается от эндпоинта, который принадлежит
  другому пользователю или доступен ему.
- Платформа: хранилище ключей и буфер обмена принадлежат сессии пользователя; любое приложение в
  этой сессии может до них достать.

Кратко модель описана в [Security](../security.md), правила эндпоинта - в
[Local API](local-api.ru.md).
