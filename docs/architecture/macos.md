# macOS

[Русский](macos.ru.md) | English

On macOS the daemon is the device: it runs as `unisond` from the app bundle, holds the Keychain
items, watches the pasteboard and serves the local API on a unix socket. The desktop app is its
client.

```
Unison.app
  Contents/MacOS/Unison                 Tauri shell, the window
  Contents/MacOS/unisond                the daemon, universal binary
  Contents/Library/LaunchAgents/        the login item of the daemon
  Contents/Resources/                   the frontend
```

## Platform ports

`platform/darwin` provides two of the four ports. Both use cgo, so the daemon that is meant to run
is built with `CGO_ENABLED=1`.

### Keystore

`platform/darwin/keystore` stores every secret as a generic password item in the Keychain:

- the service identifies the application and the account is the secret name;
- items are readable after the first unlock of the login session, never leave the device and are not
  synced to iCloud;
- the keystore is opened once, the default keychain of the process or the login keychain of the
  user, and the keychain is named in every query, so the API never looks for a keychain of its own
  and never raises a dialog that asks for one.

| Service | Data directory |
|---------|----------------|
| `app.unison` | the default data directory |
| `app.unison.dev.<slug>` | any other data directory |
| `app.unison.dev.<slug>-<hash>` | a directory whose name had to be sanitized |

The slug is lower case letters, digits and single dashes, cut to 24 characters, and the hash tells
apart directories that share a slug. A directory always maps to the same name, so repeated runs edit
the same items instead of adding new ones under a new name.

Without cgo the operations return `ErrUnsupported`; a build that cannot open a keychain returns
`ErrNoKeychain` and the daemon exits with that error. The integration tests use the fixed services
`app.unison.test.keychain` and `app.unison.test.isolation` behind the `keychaintest` build tag, so
`just test` never touches the Keychain.

### Clipboard

`platform/darwin/clipboard` implements the pasteboard. The pasteboard has no change notification, so
the watcher polls the change counter every 300 ms.

- text, HTML, a PNG image and the file URLs of every item are read;
- a screenshot offers both `public.png` and `public.tiff`: the PNG is taken as is, a TIFF alone is
  converted to PNG within the image limits of the pipeline;
- a copied file arrives as its path, so copying a large file does not read it here;
- directories are left out;
- content tagged with `org.nspasteboard.ConcealedType`, `TransientType` or `AutoGeneratedType` is
  reported as sensitive and its payload is never read;
- own writes carry `app.unison.origin`, so the pipeline ignores them.

`AccessBehavior` reports the system policy for programmatic reads, and `unisond` logs a warning at
startup when reads may show an alert or be refused. The pasteboard integration tests are behind the
`pasteboardtest` build tag and put the clipboard content back when they end.

## Daemon

`just build-unisond-host` builds the daemon for the host with cgo and the Keychain. On macOS a bare
daemon started from a terminal belongs to the terminal for the local network permission, and macOS
refuses it the local network even when the terminal has the permission. So the host build is a
bundle, `bin/unisond.app`, with the identifier `app.unison.unisond.dev`, and `bin/unisond` is a link
to its binary. `just run-daemon` starts that bundle through LaunchServices.

The bundle keeps one identity across rebuilds:

- a fixed Mach-O UUID;
- a signature with the first `Apple Development` identity of the keychain, or
  `UNISON_DEV_SIGN_IDENTITY` when it is set;
- a registration with LaunchServices.

Without an identity the bundle is signed ad-hoc and the Keychain asks after each build.

The daemon takes `--data-dir`, `--endpoint`, `--clipboard`, `--name`, `--log-level` and
`--log-stderr`, and the data directory is `~/Library/Application Support/Unison` by default. See
[Daemon and local API](local-api.md#command).

## Packaging

`just package-macos` builds the app with the daemon inside it, signs both, and writes
`packaging/macos/build/Unison.app` and `packaging/macos/build/Unison-<version>.dmg`. The version
comes from the `VERSION` file for the bundle, the disk image and the daemon.

The daemon is a universal arm64 and x86_64 binary, because it uses cgo for the Keychain and the
pasteboard and both slices are built on macOS and merged with `lipo`. The app is built for the host
architecture; `just package-macos --universal` builds it universal as well.

### Login item

`Contents/Library/LaunchAgents/app.unison.unisond.plist` makes the daemon a login item of the
bundle: `BundleProgram` points at `Contents/MacOS/unisond`, the job starts at login, and launchd
restarts it after a crash.

The app registers the login item with `SMAppService` on the first launch of a packaged build, and
the startup toggle of the settings screen registers and unregisters it afterwards. A system that
asks for approval reports `requires-approval` until the user allows the item. When the login item is
off, the app starts the daemon of the bundle for the rest of the session.

`--login-item=status`, `--login-item=register` and `--login-item=unregister` change the login item
from the command line, which is how a packaged app is checked without the window. The login item
needs an Apple-issued signature: an ad-hoc build can register it, but launchd then refuses to start
the job with exit code 78.

### Info.plist and entitlements

The Info.plist declares `NSLocalNetworkUsageDescription` and `NSBonjourServices` with
`_unison._udp`, `_unison-pair._udp` and `_unison-friends._udp`, because the daemon of the bundle does
the discovery.

The bundle is signed with the hardened runtime and the entitlements in
`desktop/src-tauri/entitlements.plist`: network client for the paired devices and the local API,
network server for the QUIC listener.

### Signing and notarization

Credentials come from the environment and are never stored:

```sh
export UNISON_MACOS_SIGN_IDENTITY="Developer ID Application: Name (TEAMID)"
xcrun notarytool store-credentials unison-notary --apple-id you@example.com --team-id TEAMID
export UNISON_MACOS_NOTARY_PROFILE=unison-notary
just package-macos
```

`UNISON_MACOS_APPLE_ID`, `UNISON_MACOS_APPLE_PASSWORD` and `UNISON_MACOS_TEAM_ID` notarize with the
account directly instead of a keychain profile. `UNISON_MACOS_SKIP_NOTARIZE=1` stops after signing
and `--no-dmg` builds the app only. Without `UNISON_MACOS_SIGN_IDENTITY` the app is signed ad-hoc,
which is enough to build and run the bundle on the building machine but not for distribution.

The daemon is signed under `app.unison.unisond`, and the Keychain items belong to that identity. A
change of the signing identity makes macOS ask for access to the existing items, and an ad-hoc
rebuild changes it on every build. Keep the identifier and the certificate stable across releases.

`just verify-macos [path]` checks the layout, the login item property list, the Info.plist keys, the
entitlements, the hardened runtime and the signature, and prints the checks that need a second
machine: the local network prompt, the daemon after a re-login, and the clipboard between two
devices.

## Name of the device

The name of the device comes from the local API and is stored in the `device.name` setting. Without
a stored name the daemon uses the host name, `--name` overrides it for one run, and a rename from
the app changes it for the next start.
