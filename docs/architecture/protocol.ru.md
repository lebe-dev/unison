# Протокол

Русский | [English](protocol.md)

Два устройства говорят на трех слоях под буфером обмена и файлами: QUIC, аутентификация
транспорта и сессия. Все, что выше них, - это protobuf-сообщение, определенное в
`proto/unison/wire/v1`.

```
clip, history, blob, share        domain handlers
session                            control stream, request and transfer streams
transport                          QUIC, TLS 1.3, certificates, auth proof
QUIC / UDP (+ relay datagrams)
```

## Версия протокола

Одна версия покрывает протокол пиров и протокол ретранслятора. Она хранится в `core/protocol`, и
сейчас ее значение - `1`. Поднимайте ее, когда изменение несовместимо с прежней версией.

Каждый клиент проверяет полученную версию:

| Клиент | Проверка |
|--------|----------|
| демон и мобильное ядро | `Hello` пира |
| клиент ретранслятора | `RegisterResult` ретранслятора |
| сервер ретранслятора | `Register` клиента |

Пир с той же версией продолжает работу. О пире с другой версией сообщается: если пир новее, обновить
нужно этот клиент; если старее, обновить нужно пир. Демон передает направление через локальный API,
поэтому его показывают командная строка, приложение для компьютера и приложение для Android;
ретранслятор пишет это в лог.

## Транспорт

`core/transport` ведет соединения пиров по QUIC. Обе стороны предъявляют самоподписанный
сертификат своей идентичности устройства; сертификат несет публичные ключи Ed25519 и ML-DSA-65 и
выведенный из них ID устройства.

| Свойство | Значение |
|----------|-------|
| TLS | 1.3, взаимные сертификаты, без session tickets |
| Обмен ключами | только X25519MLKEM768, без классического отката |
| ALPN, пиры | `unison/1` |
| ALPN, спаривание | `unison-pair/1` |
| Keepalive | 25 с |
| Таймаут простоя | 60 с |
| Таймаут рукопожатия | 10 с |
| Входящие потоки | 32 двунаправленных, 128 однонаправленных |
| Размер пакета | от 1200 до 1452 байт |

Оба сертификата самоподписанные и несут ID устройства как common name. Клиент не проверяет
цепочку CA: решение о доверии принимает `PeerVerifier`, дважды. Он выполняется во время
рукопожатия, чтобы отказать неизвестному или отозванному устройству, и после него, чтобы собрать
идентичность и роль; оба вызова должны принять, а реализация отказывает в безопасную сторону.
Соединение, рукопожатие которого не использовало гибридный обмен ключами, закрывается с
`CodeInsecure` (`0x02`).

Первый поток соединения пира несет доказательство аутентификации. Обе стороны подписывают
`EKM(32) || role(1) || device_id(32)` ключом ML-DSA-65, где EKM берется из экспортера TLS с
меткой `unison/1 auth`. Кадр фиксирован на 3343 байтах, поэтому он привязывает ключ идентичности к
секрету экспортера, роли и ID устройства, и записанную сессию нельзя повторить в другом
соединении. Каждая сторона сверяет роль пира со своей записью доверия. Доказательство, которое не
проверяется, закрывает соединение с `CodeAuthFailed` (`0x01`).

Слушатель спаривания - это отдельный слушатель с ALPN спаривания. Он принимает неизвестные
сертификаты и оставляет решение `PairingPolicy`: `AcceptPairingPeer` для потока с коротким кодом
или `PinCertificate(fingerprint)` для потока с QR. Слушатель существует только пока открыто окно.

## Сессия

`core/session` ведет протокол пиров на аутентифицированном соединении.

Сессия начинается с `Hello` в потоке управления, то есть в потоке, который уже нес
доказательство аутентификации. Обе стороны объявляют:

- версию протокола, сейчас `1`, из `core/protocol`;
- имя устройства, не больше 128 байт;
- платформу;
- локальную политику буфера обмена;
- до 32 имен возможностей, каждое не больше 64 байт.

Пир с другой версией получает событие `peer-needs-update`, и соединение закрывается кодом `0x10`;
событие и лог сообщают, новее ли пир, то есть обновить нужно этот клиент, или старее, то есть
обновить нужно пир. Искаженный Hello или другое нарушение протокола закрывает соединение с `0x11`, а
обработчик, который паникует, завершает сессию с `0x12`, но никогда не процесс.

### Кадрирование

Каждое сообщение - это uvarint длины полезной нагрузки, за которым идет protobuf-полезная
нагрузка. Длина проверяется по лимиту до выделения памяти под полезную нагрузку.

| Кадр | Лимит |
|-------|-------|
| Управляющее сообщение | 1 MiB |
| Кадр потока | 2 MiB |

### Управляющие сообщения

Поток управления двунаправленный и несет конверты `ControlMessage`. Вариант полезной нагрузки
выбирает обработчик, а возможность пира должна разрешать действие до запуска обработчика.

| Вид | Возможность | Назначение |
|------|------------|---------|
| `hello` | - | версия протокола, имя, платформа, политика |
| `clip-announce` | `receive-clip-announce` | элемент буфера обмена |
| `history-sync` | `sync-history` | вектор версий истории |
| `history-batch` | `sync-history` | записи истории, которых не хватает пиру |
| `have-blob` | `fetch-blob` | спрашивает, сохранен ли blob |
| `have-blob-resp` | `fetch-blob` | отвечает на запрос blob |
| `share-offer` | авторизует сервис отправки файлов | предлагает файлы |
| `share-decision` | нет | принимает или отклоняет предложение |
| `share-cancel` | нет | останавливает передачу |
| `share-result` | нет | сообщает отправителю результат |
| `introduction` | `introduce` | представляет другое устройство Personal |
| `revocation` | `revoke` | отзывает устройство группы |
| `gossip-digest` | `introduce` | состояние доверия устройства |
| `gossip-records` | `introduce` | данные доверия, которых не хватает пиру |
| `set-peer-policy` | `set-remote-policy` | просит устройство изменить флаг подтверждения |
| `peer-policy` | `set-remote-policy` | сообщает флаги подтверждения отправителя |
| `mediated-offer` | авторизует сервис знакомства | предлагает знакомство через отправителя |
| `mediated-ready` | авторизует сервис знакомства | одно устройство приняло до того, как другое прислало ключи |
| `mediated-commit` | авторизует сервис знакомства | эфемерные ключи устройства с меньшим ID |
| `mediated-finish` | авторизует сервис знакомства | эфемерные ключи устройства с большим ID |
| `mediated-cancel` | авторизует сервис знакомства | завершает знакомство |
| `mediated-result` | авторизует сервис знакомства | сообщает, что новое устройство сохранено |

Доказательство аутентификации не является управляющим сообщением: это фиксированный кадр,
который транспорт читает до старта сессии, а вид `auth-proof` существует только для резерва слота.

Матрица возможностей лежит в `core/trust`. Роль решает каждое действие:

| Действие | Personal | Personal с флагом | Friends |
|--------|----------|--------------------|---------|
| receive-clip-announce | allow | allow | deny |
| apply-clipboard | allow | confirm | deny |
| sync-history | allow | allow | deny |
| fetch-blob | allow | allow | deny |
| receive-share | allow | confirm | confirm |
| receive-files | allow | confirm | confirm |
| introduce, revoke, set-remote-policy | allow | allow | deny |
| mediated-pair | confirm | confirm | confirm |

Сообщение, которое матрица запрещает, отбрасывается и засчитывается как нарушение. Три нарушения
завершают сессию. Объявления clip дополнительно ограничены частотой 5 в секунду с всплеском 10.

### Потоки

Потоки запросов двунаправленные и несут один запрос с ответом; потоки передачи однонаправленные и
несут одну передачу. Первый кадр - это `StreamHeader`:

| Поле | Смысл | Лимит |
|-------|---------|-------|
| `kind` | запрос или передача | обязательно |
| `payload_type` | выбирает зарегистрированный обработчик | 64 байта |
| `transfer_id` | группирует потоки одной передачи | 128 байт |

| Тип полезной нагрузки | Вид | Обработчик |
|--------------|------|---------|
| `blob.request` | запрос | сервис передачи blob |
| `share.request` | запрос | сервис отправки файлов |

Одновременно обслуживается не больше 16 потоков запросов и 32 потоков передачи. Заголовок потока
должен прийти за 10 с. Поток освобождает свой слот соединения только когда закрыты оба
направления, поэтому сессия отбрасывает читающую сторону запроса, как только его обработчик
закончил.

## Соединения

Узел держит ровно одно соединение на спаренное устройство. Одновременный дозвон разрешается
сравнением ID устройств: обе стороны оставляют соединение, которое инициировало устройство с
меньшим ID, и это устройство дозванивается снова, когда оно онлайн по соединению, которое
инициировала другая сторона.

Адреса берутся из четырех мест, в этом порядке предпочтения:

1. ручной адрес, сохраненный с устройством;
2. кандидаты из обнаружения mDNS;
3. кеш адресов пира;
4. ретранслятор.

Узел дозванивается с сокета основного слушателя, поэтому адрес, с которого подключился пир, - это
адрес, по которому до него можно дозвониться обратно. Устройство старой версии дозванивается с
эфемерного порта, который не принимает соединений, поэтому адрес входящего соединения кешируется
последним и только для хоста, которого в кеше еще нет. Адрес, до которого удалось дозвониться,
вытесняет другие порты своего хоста: они остались от прежнего запуска. Порт основного слушателя
сохраняется в `transport.main_port`, поэтому кешированный адрес устройства переживает перезапуск.
Попытка подключения прекращается, как только пир подключился сам. После потерянного соединения узел
переподключается с задержкой, которая удваивается от одной секунды до тридцати; для пира, который
остается офлайн, приложение Android дает задержке вырасти до пяти минут, потому что обнаружение,
смена сети и сам пир возвращают его раньше. `NetworkChanged` объявляет устройство заново и повторяет
попытку для каждого офлайн-пира.

Путь выбирается для каждого устройства отдельно, поэтому узел держит соединения по локальной сети и
через relay одновременно: телефон может держать ноутбук из той же сети на локальном пути и
связываться с компьютером в другом месте через relay. Пока устройство на связи через relay, узел
продолжает искать его в локальной сети с задержкой, которая удваивается от одной секунды до
тридцати; смена сети сбрасывает задержку, а обнаружение набирает появившееся устройство сразу.
Обнаруженный адрес запоминает устройство, которое на нем ответило, и не набирается ради другого
устройства, пока это на связи в локальной сети: рукопожатие нашло бы то же устройство. Новое
объявление адреса стирает эту запись.

## Обнаружение

`core/discovery` говорит на DNS-SD в локальной сети, без библиотеки, через собственные сокеты
mDNS.

| Сервис | Тип | Когда |
|---------|------|------|
| main | `_unison._udp.local.` | пока узел работает |
| pairing | `_unison-pair._udp.local.` | пока открыто окно спаривания |
| friends | `_unison-friends._udp.local.` | пока идет поиск Friends |

Объявление не несет ни имени, ни ID устройства, ни роли: TXT-запись держит `v=1` и, для сервиса,
у которого есть ключи, один или несколько тегов. Теги - это то, что устройство сверяет с
известными ему ключами:

- сервис main несет тег ключа обнаружения группы Personal;
- сервис friends несет по одному тегу на пару Friends, выведенному из ключа рандеву пары;
- сервис pairing не несет тега, потому что устройство, открытое для спаривания, еще не
  доверенное.

Тег - это HMAC-SHA-256 от десятиминутной эпохи, усеченный до 8 байт и записанный как 13 символов
base32 в нижнем регистре. Устройство принимает эпохи предыдущих, текущих и следующих десяти
минут, поэтому расхождение часов не важно и проворот никогда надолго не ломает обнаружение.
Проворот ключа группы принимает предыдущий ключ на переходный период.

Имя экземпляра сервиса, имя хоста и запрос - обычный DNS-SD; записи PTR и TXT живут 4500 с, SRV
и адресные записи - 120 с. Объявления посылаются дважды, с интервалом в одну секунду, а эпоха и
набор интерфейсов перепроверяются каждые 30 с. Браузер повторяет запрос через секунду после первого
и удваивает паузу до одной минуты, как требует RFC 6762, потому что каждый запрос будит телефоны в
сети; смена сети или эпохи начинает расписание заново.

`LocalNetworkBlocked` сообщает о процессе, которому система отказывает в отправке в локальную
сеть, пока loopback еще работает, - так macOS делает без разрешения на локальную сеть.

## Спаривание

`core/pairing` реализует окно, короткий код и QR-код.

| Лимит | Значение |
|-------|-------|
| Окно | 3 минуты, можно продлить |
| Таймаут обмена | 2 минуты |
| Ожидающих обменов | 8 |
| Соединений на окно | 4 за 10 секунд |

Короткая строка аутентификации вычисляется из экспортера TLS (`unison/1 sas`, 32 байта) и
идентичностей обоих сертификатов: шесть десятичных цифр и четыре emoji из фиксированной таблицы
на 64. Устройство между двумя получает разные коды на двух экранах, а сообщение спаривания,
которое называет не ту идентичность, что в сертификате его соединения, отклоняется до показа кода.

QR-код несет ID устройства, отпечаток сертификата, случайный одноразовый токен, адреса слушателя
спаривания и роль, которую предлагают. Сканирующее устройство закрепляет отпечаток, поэтому
отказывает любому другому сертификату, и отправляет токен с запросом, подписанным своими ключами
идентичности. Токен принадлежит одному окну, принимается один раз и заменяется после завершенного
спаривания.

Сообщение спаривания - это uvarint длины и protobuf-полезная нагрузка не больше 64 KiB. Обмен
состоит из `PairRequest`, `PairResponse`, `PairDecision` и `PairAccept`; последний несет ключ
рандеву пары и, для пира Personal, ключ обнаружения и до 64 представлений. Никакие данные группы
не отправляются до того, как обе стороны приняли.

URI кода - `unison://pair` с параметрами `v`, `id`, `fp`, `t`, `a` и `role`. Он не больше 512
байт и несет не больше четырех адресов, каждый - IP-адрес с портом, поэтому сканирующее
устройство подключается по адресу, а не ищет сеть.

Результат обоих потоков - запись доверия: публичные ключи, имя, платформа, роль и время последней
доступности. Окно спаривания - еще и единственное время, когда существует слушатель спаривания.

## Обмены доменов

### Буфер обмена

`clip-announce` несет метаданные элемента и его представления, когда полезная нагрузка достаточно
мала, чтобы ехать внутри. Элемент больше 64 KiB несет только хеши, и получатель загружает
полезную нагрузку по протоколу blob. Объявление от устройства, которому Unison писал сам,
игнорируется на источнике.

### История

Когда открывается сессия с пиром Personal, обе стороны шлют `history-sync` с вектором версий
своей истории. `history-batch` отвечает записями, которых не хватает пиру, от старых к новым, до
64 записей или 512 KiB на пакет и до 4096 записей и 16 MiB на обмен, поэтому большой разрыв
заполняется за несколько обменов. Полезные нагрузки в обмен не входят: они загружаются как blob.

### Blob

`have-blob` спрашивает, хранит ли пир blob, `have-blob-resp` отвечает на это числом чанков. Сама
полезная нагрузка тянется потоками `blob.request` по типу полезной нагрузки запроса:

1. получатель просит диапазон не больше 64 чанков, при желании только дерево;
2. ответ начинается с дерева Bao blob, не больше 2 MiB; дерево blob больше размера, объявленного
   в элементе или предложении, отбрасывает источник до того, как что-либо сохранено;
3. чанки идут в порядке возрастания индекса;
4. каждый чанк проверяется по дереву до записи.

Загрузка использует не больше 16 источников и 2 одновременных запросов на пира и отбрасывает
источник, который прислал поврежденный, не по порядку или неожиданный кадр. Тот же механизм
обслуживает принятую отправку файлов с типом полезной нагрузки `share.request` и ID передачи
предложения.

### Отправка файлов

Отправитель предлагает файлы через `share-offer`. Матрица доверия решает ответ: пир Personal без
флага файлов принимается сразу, пир Personal с флагом и пир Friends ждут пользователя, а пир,
которому матрица отказывает, получает отказ. Затем получатель применяет сетевую политику к
предложению, принятому сразу, с общим размером файлов: больше лимита ячейки `files` или через
ретранслятор, пока файлы идут по нему только по запросу, предложение ждет пользователя, а ячейка
`reject` его отклоняет. Файлы скачиваются с размерами из предложения как ограничением. `share-decision` несет ответ, `share-cancel`
останавливает передачу с любой стороны, а `share-result` сообщает отправителю результат.

### Доверие

`introduction` представляет другое устройство Personal, поэтому достаточно спариться с одним
устройством группы. `revocation` несет подписанный отзыв, который любое устройство Personal может
выпустить для любого устройства группы. `gossip-digest` и `gossip-records` подтягивают
устройство, которое отсутствовало, до состояния доверия группы: digest несет только верхушки
записей, ответ несет не больше 16 записей на сообщение и 512 на digest, а сессия отвечает не
больше чем на 8 digest. `set-peer-policy` меняет флаги подтверждения пира для локального
устройства, а `peer-policy` сообщает флаги отправителя после изменения и при открытии сессии.

В gossip и синхронизации истории участвуют только сессии Personal. Запись применяется, только
когда ее издатель - сохраненное, неотозванное устройство Personal, а подпись и метка времени
проверяются, поэтому представление или отзыв нельзя подделать устройством Friends.

### Знакомство через доверенное устройство

`core/mediate` знакомит два устройства через спаренное устройство, которое знает оба. Сообщения
идут по двум уже открытым сессиям, поэтому обмену не нужны ни обнаружение, ни окно спаривания.
Узел объявляет в Hello возможность `mediated-pair/1`, а посредник отказывает участнику, который ее
не объявил, с `ErrUnsupportedPeer`. Версия протокола остается `1`, поэтому старый клиент продолжает
работать и просто не может участвовать.

Участники упорядочены по своим 32-байтным ID устройств: меньший - это `X`, больший - `Y`. Оба
предложения несут одну и ту же запись, поэтому посредник подписывает ее один раз. Длины - явные
целые big-endian, строка - это длина `uint16` и ее байты, а адреса - счетчик `uint16` и строки с
длиной `uint16`:

```
offer  = version(1) || session_id(16) || idB(32) || idX(32) || idY(32) || role(1) || expires_at(8)
commit = offer || x25519_X(32) || mlkem_ek_X(1184) || platform_X(1) || name_X || addrs_X
finish = offer || x25519_X(32) || mlkem_ek_X(1184) || x25519_Y(32) || mlkem_ct_Y(1088)
         || platform_Y(1) || name_Y || addrs_Y
```

`X` подписывает commit с `mediated-pair-commit`, `Y` подписывает finish с `mediated-pair-finish`, а
посредник подписывает offer с `mediated-pair-offer`. Каждая подпись гибридная, Ed25519 и ML-DSA-65.
Finish повторяет эфемерные ключи `X`, поэтому посредник не может подменить их по пути, а каждый
участник проверяет подпись другого по всей записи до того, как что-либо сохранить.

`X` создает эфемерную пару X25519 и пару ключей ML-KEM-768, а `Y` создает пару X25519 и выполняет
инкапсуляцию в ключ ML-KEM устройства `X`. Оба выводят 32-байтный ключ рандеву:

```
BLAKE3("unison/1 mediated-rendezvous" || offer || x25519_X || mlkem_ek_X ||
       x25519_Y || mlkem_ct_Y || ss_x25519 || ss_mlkem)
```

Посредник несет публичные ключи и запись, но не видит ни одного общего секрета, поэтому не может
вывести ключ. Эфемерные приватные ключи и оба общих секрета затираются, когда ключ выведен или обмен
завершен.

Проверочный код - это `BLAKE3("unison/1 mediated-sas" || version || session_id || idB || PK_X ||
PK_Y || role)`, отформатированный как шесть цифр и четыре emoji по таблице кода спаривания. Он
покрывает оба полных ключа идентичности, поэтому два участника видят один код, только когда
согласны в посреднике, друг в друге и роли.

Обмен завершается сообщением `mediated-result` от `X` после того, как `X` сохранил нового пира.
Отказ, срок или закрытая сессия отправляют `mediated-cancel` с причиной, и в хранилище доверия
ничего не пишется. Сообщение, которое не проходит проверку, отбрасывается, и тогда обмен
заканчивается по сроку. Протокол не несет ни ключа обнаружения, ни адреса ретранслятора, ни его
токена, и в нем нет сообщения, которое перечисляет пиров посредника.

## Лимиты

| Лимит | Значение |
|-------|-------|
| Управляющее сообщение | 1 MiB |
| Кадр потока | 2 MiB |
| Потоков запросов в работе | 16 |
| Потоков передачи в работе | 32 |
| Нарушений протокола | 3 |
| Объявлений clip | 5 в секунду, всплеск 10 |
| Таймаут заголовка потока | 10 с |
| Таймаут Hello | 10 с |
| Событий сессии в буфере | 16 |
| Обменов знакомства на посредника | 4, по одному на пару |
| Ожидающих предложений знакомства | 4, по 2 на посредника |
| Предложений знакомства от одного посредника | 1 за 15 с, всплеск 2 |
| Время жизни обмена знакомства | 3 мин |
| Запомненных ID обменов | 256 на 10 мин |
| Адресных подсказок в сообщении знакомства | 4, по 64 байта |
