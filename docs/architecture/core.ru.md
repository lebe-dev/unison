# Ядро

Русский | [English](core.md)

`core/` - это набор пакетов Go, которые вместе образуют одно устройство. Все их знает только
`core/node`; пакет домена достает до остальных через интерфейсы, которые передает узел. В
`core/ports` лежат интерфейсы к операционной системе, поэтому все остальное собирается и
работает на любом хосте.

## Пакеты

| Пакет | Ответственность |
|---------|----------------|
| `identity` | пара ключей, ID устройства, гибридные подписи, TLS-сертификат |
| `trust` | записи пиров, роли, матрица возможностей, секреты группы |
| `store` | SQLite с шифрованием на диске, миграции, настройки |
| `session` | протокол пиров поверх потоков QUIC |
| `transport` | QUIC с mutual TLS и доказательством аутентификации |
| `discovery` | объявления и поиск mDNS/DNS-SD |
| `pairing` | окно спаривания, короткий код и QR-код |
| `mediate` | знакомство двух устройств через третье |
| `policy` | роль, сеть и размер в действие |
| `clip` | конвейер буфера обмена в обе стороны |
| `blob` | контентно-адресуемое хранилище с шифрованием и проверкой |
| `blob/transfer` | потоки запросов blob между пирами |
| `history` | журнал только на добавление, его вектор версий и TTL |
| `share` | предложения файлов и их передача |
| `download` | безопасные имена и отметка скачанного файла |
| `gossip` | распространение записей доверия и данных группы по сессиям |
| `relay` | клиент ретранслятора и его виртуальное пакетное соединение |
| `api` | сервис локального API, `api/localconn` - его эндпоинт |
| `ports` | интерфейсы к операционной системе |
| `node` | композиция всего перечисленного |
| `model` | типы доменов, `model/protoconv` отображает их в protobuf |

## Композиция узла

`node.New(node.Config{...})` принимает каталог данных, имя устройства и платформу, порты
платформы (хранилище ключей, буфер обмена, обнаружение), необязательные часы и логгер, лимиты
соединений и функцию, которая связывает пакетные соединения, - так тест запускает узел в
виртуальной сети.

`Start` открывает базу с миграциями доменов trust, clipboard, blob и history, загружает
идентичность, привязывает основной слушатель к сохраненному порту и второй сокет для исходящих
соединений, объявляет устройство, открывает blob-хранилище с сервисом передачи и загрузчиком,
читает настройки политики и истории и запускает конвейер буфера обмена. `Stop` завершает сессии,
сокеты, обнаружение и базу.

Узел владеет:

- соединениями: по одному на спаренное устройство, с переподключениями, выбором пути и кешем
  адресов;
- окном спаривания и преобразованием его событий;
- шиной событий и ее подписчиками;
- состоянием сети и решателем из `core/policy`;
- blob-хранилищем, загрузчиком и списком пиров, которые могут отдать blob;
- журналом истории и его синхронизацией;
- конвейером буфера обмена и сервисом отправки файлов.

`AddSessionHook` регистрирует обработчик на каждой новой сессии - так буфер обмена, передача
blob, сервис отправки файлов и gossip подключаются к протоколу. Обработчики нужно
зарегистрировать до открытия сессии, потому что пир может прислать сообщения сразу после своего
Hello.

`Subscribe` возвращает подписчика с собственной очередью событий, поэтому медленный читатель
теряет события, а не тормозит ядро. Среди событий `peer-online`, `peer-offline`, `clipboard`,
`clip-download`, `clip-apply`, `peer-incompatible`, `transfer`, `history` и события спаривания.

## Хранилище

`core/store` открывает `<data dir>/unison.db` и держит ключ шифрования данных в хранилище ключей
платформы. Каждое чувствительное значение запечатано этим ключом, идентификаторы, нужные для
запроса, остаются читаемыми, а потеря ключа делает базу нечитаемой: хранилище возвращает
`ErrDEKMissing` вместо того, чтобы стартовать с пустыми данными.

| Свойство | Значение |
|----------|-------|
| Драйвер | `modernc.org/sqlite`, без cgo |
| Соединение на запись | одно, транзакции сериализованы |
| Пул чтения | 8 соединений, только чтение |
| Таймаут занятости | 5 с |
| Режим журнала | WAL, `synchronous=NORMAL` |
| Ключ шифрования данных | 32 случайных байта под `store.dek` |
| Миграции | SQL только вперед, один блок на домен |

Открытым текстом лежат только те столбцы, по которым идет запрос: идентификаторы, устройство
источника, порядковые номера, время истечения и хеши blob. Все остальное запечатывает `Sealer`,
который привязывает шифртекст к своей таблице и ключу строки через XChaCha20-Poly1305 и AAD из
`table + row key`, поэтому значение нельзя перенести в другую строку.

Каждый домен встраивает свои миграции и передает их в `store.Options.Migrations`. База
записывает каждую примененную версию, поэтому миграция, добавленная позже, все равно выполнится
на базе, где уже есть версии выше.

| Домен | База | Таблицы |
|--------|------|--------|
| `store` | 0 | `settings` |
| `trust` | 100 | `peers`, `group_secrets`, `introductions`, `revocations` |
| `clip` | 200 | `clip_seq` |
| `blob` | 400 | `blob_meta` |
| `history` | 500 | `history_items`, `history_blobs`, `history_vectors` |

База разводит номера версий доменов, поэтому миграцию можно добавить в нижний блок даже тогда,
когда в базе уже есть верхние.

Настройки - это типизированные значения с ключом. Ключи, которые читает ядро:

| Ключ | Смысл |
|-----|---------|
| `device.name` | имя, которое объявляет устройство |
| `transport.main_port` | сохраненный порт слушателя |
| `blob.max_size` | лимит blob-хранилища в байтах |
| `history.ttl.text` / `.image` / `.files` | время жизни записанных элементов |
| `share.downloads_dir` | каталог, который принимает отправленные файлы |
| `policy.network.<condition>.<kind>.mode` / `.max_size` | одна ячейка сетевой политики |
| `policy.network.<condition>.relay` | разрешен ли ретранслятор при условии |
| `policy.relay.max_size`, `policy.relay.files_on_request` | лимиты ретранслятора |
| `clip.pause.active`, `clip.pause.until` | пауза буфера обмена |
| `sentry.enabled` | согласие на отправку ошибок |

## Идентичность и доверие

`core/identity` создает пару ключей Ed25519 и ML-DSA-65 при первом запуске. Семена лежат в
хранилище ключей под `identity/ed25519-seed` и `identity/mldsa65-seed`, а ID устройства - это
первые 32 байта BLAKE3 по обоим публичным ключам. Гибридные подписи несут обе части, и пир
принимает их, только когда проверяются обе; типы подписи разделяют домены разных сообщений.

`core/trust` записывает, какие устройства доверенные и что каждому разрешено. Запись пира хранит
идентичность, роль, назначенную при спаривании, флаги локального подтверждения, кеш адресов и
время последней доступности. Отозванное устройство остается в таблице как запись deny-list и
больше никогда не становится доверенным. Публичные ключи и столбцы фильтрации лежат открытым
текстом, профиль и кеш адресов запечатаны.

Группа Personal делится своими секретами через `group_secrets`: ключом обнаружения группы и
ключом рандеву каждой пары. Представления распространяют новое устройство Personal на остальную
группу, поэтому достаточно спариться с одним устройством. Завершенное спаривание записывает
представления обеих сторон, поэтому устройство, начавшее обмен, тоже распространяет новое
устройство, а узел объявляет себя заново под ключом обнаружения группы. Отзыв подписывает
устройство, которое его выпускает, и он распространяется так же. Отзыв устройства Personal
проворачивает ключ обнаружения, и предыдущий ключ еще час продолжает совпадать с тегами
обнаружения.

Пир держит не больше 8 кешированных адресов, группа держит не больше 4096 представлений и 4096
отзывов, а подписанная запись, время которой больше чем на 24 часа в будущем, отклоняется.

Матрица возможностей - чистая функция от записи пира, она лежит в `core/trust/action.go` и описана
в [Протоколе](protocol.ru.md#управляющие-сообщения).

## Знакомство через доверенное устройство

`core/mediate` позволяет спаренному устройству познакомить два устройства, которые оно знает.
Сервис одновременно выступает посредником и участником обмена, а свои обработчики сообщений он
регистрирует на каждой сессии, как и другие домены.

Сервис владеет:

- каноническими записями offer, commit и finish и гибридными подписями над ними;
- эфемерными ключами X25519 и ML-KEM-768, ключом рандеву, который выводят оба участника, и
  проверочным кодом, который они показывают;
- состоянием посредника, который пересылает commit и finish без изменений, следит за двумя
  участниками и завершает обмен по сроку или когда закрывается сессия;
- состоянием участника, который проверяет предложение по локальному хранилищу доверия, применяет
  лимиты и кеш повторов, показывает предложение пользователю и одной операцией сохраняет нового
  пира с его ключом рандеву и адресными подсказками;
- проверкой имен и адресных подсказок, чтобы пир не мог подсунуть невидимое имя, DNS-имя, зону,
  multicast или неподходящий loopback-адрес.

Сервис читает и пишет через два узких интерфейса: `Store`, который реализует `*trust.Store`, и
`Sessions`, который выдает открытую сессию устройства. Эфемерные ключи и обмены живут только в
памяти, а `Stop` их затирает.

`core/node` создает сервис в `openMediate`, добавляет `mediated-pair/1` к объявляемым возможностям и
регистрирует `installMediate` как хук сессии. Методы узла `StartMediatedPair`, `ConfirmMediatedPair`,
`RejectMediatedPair`, `CancelMediatedPair` и `MediatedPairs` - это API сервиса, а
`supports_mediated_pair` устройства истинно, пока его сессия объявила возможность. События
`mediated-pair-offer`, `mediated-pair-updated`, `mediated-pair-completed` и
`mediated-pair-canceled` несут снимок обмена. Когда обмен завершен, узел включает поиск устройств
друзей, если пользователь об этом попросил, синхронизирует связи и для пары Personal уведомляет
gossip.

## Конвейер буфера обмена

`core/clip` превращает изменение буфера обмена в элемент clip и применяет приходящие элементы.

Захват:

- изменение объединяется с изменениями, случившимися ближе 250 мс, и создается как один элемент;
- собственные записи игнорируются 2 с после записи;
- содержимое, которое платформа помечает как чувствительное, отбрасывается до чтения его
  полезной нагрузки;
- текст сохраняет простой текст и HTML, изображение нормализуется в PNG, а исходный формат
  едет вторым представлением, пока он меньше двойного размера PNG;
- изображения больше 24 мегапикселей, больше 8192 пикселей по стороне или больше 64 MiB
  пропускаются;
- полезная нагрузка до 64 KiB едет внутри объявления, большая уходит в blob-хранилище;
- файл хешируется в фоновой очереди и объявляется, когда его хеш готов.

Входящие элементы решает `core/policy`:

| Действие | Эффект |
|--------|--------|
| reject | элемент отбрасывается и не записывается |
| metadata | элемент записывается, полезная нагрузка загружается, когда пользователь попросит |
| confirm | элемент записывается и ждет пользователя |
| auto | элемент применяется сразу, в пределах лимита размера ячейки |

Пауза глушит оба направления: ничего не захватывается и не объявляется, а входящий элемент
отбрасывается, не будучи записанным.

## Политика

`core/policy` отображает роль пира, состояние сети и размер элемента в действие. `Decide` - это
чистая функция от конфигурации; `Decider` привязывает ее к живому хранилищу доверия, состоянию
сети и пути соединения и реализует `clip.PolicyDecider`, поэтому `core/clip` никогда не
импортирует `core/policy`.

| Условие | Текст | Изображение | Файлы | Ретранслятор |
|-----------|------|-------|-------|-------|
| unmetered | auto до 10 MiB | auto до 10 MiB | metadata | да |
| metered | auto до 1 MiB | auto до 1 MiB | metadata | да |
| roaming | auto до 1 MiB | metadata | metadata | нет |
| data saver | auto до 1 MiB | metadata | metadata | нет |

Решение отказывает в безопасную сторону: неизвестная роль, вид, источник или путь отклоняются.
Устройство Friends никогда не может внедрить элемент буфера обмена. Элемент, пришедший через
ретранслятор, когда строка запрещает его, отклоняется, а файлы через ретранслятор остаются
metadata, пока пользователь их не попросит. Лимиты лежат в настройках `policy.*`, и изменение
применяется к следующему элементу.

## Blob-хранилище

`core/blob` держит файлы с адресацией по содержимому. Blob адресуется хешем BLAKE3 всего
содержимого и хранится чанками по одному MiB.

- дерево Bao содержимого лежит рядом с чанками, поэтому каждый чанк проверяется по хеш-дереву до
  записи;
- каждый чанк запечатан ключом шифрования данных узла и привязан к хешу и индексу чанка;
- файл начинается с фиксированного заголовка, за которым идут дерево и запечатанные чанки;
- частичная передача держит битовую карту чанков в `blob_meta`, поэтому `WriteChunk` с
  `Complete` продолжает с того места, где остановилась;
- хранилище ограничено `blob.max_size` (2 GiB на десктопе, 500 MiB на мобильных по умолчанию) и
  вытесняет давно не использованные полные blob; закрепленные blob и частичные передачи не
  вытесняются никогда.

`core/blob/transfer` обслуживает потоки `blob.request`: получатель просит чанки по индексу,
записывает и проверяет их и держит битовую карту чанков для каждого blob, чтобы упавшее
соединение не теряло работу. Загрузка несет размер, объявленный в элементе или предложении, как
`MaxSize`; источник, чье дерево хешей описывает blob большего размера, отбрасывается с `ErrSize`
до того, как что-либо сохранено, поэтому пир не может обойти лимиты политики, объявив маленький
элемент.

## История

`core/history` - это журнал устройства: строка на устройство источника и порядковый номер
источника, плюс вектор версий, который переживает очистку истекших записей.

- захваченные и полученные элементы записываются вместе с описанием полезной нагрузки каждого
  blob, чтобы локальный API мог отличить сохраненную полезную нагрузку от той, которую еще нужно
  скачать;
- ручное удаление добавляет tombstone с id удаленного элемента, и tombstone едет как любая другая
  запись;
- срок истечения решает устройство источника и везет его в элементе, поэтому истекший элемент
  исчезает на каждом устройстве без обмена по сети;
- по умолчанию время жизни - семь дней для текста, три дня для изображений и один день для
  файлов, максимум 365 дней;
- очистка каждые десять минут удаляет истекшие записи;
- каждая запись сообщает о себе через `history.Options.OnChange`, и узел публикует это как событие
  `history`.

Когда открывается сессия с пиром Personal, обе стороны шлют свой вектор версий и отвечают
записями, которых не хватает пиру, от старых к новым, до 64 записей или 512 KiB на пакет и до
4096 записей или 16 MiB на обмен. Полезные нагрузки в обмен не входят.

## Отправка файлов

`core/share` отправляет файлы, которые выбрал пользователь. Отправитель кладет файлы в
blob-хранилище и предлагает их через `ShareOffer`; получатель отвечает `ShareDecision`. Решает
матрица доверия: пир Personal без флага файлов принимается сразу, пир Personal с флагом и пир
Friends ждут пользователя, а отказанному пиру приходит отказ. Предложение, которое матрица
принимает сразу, затем проходит сетевую политику с общим размером файлов и источником `share`:
автоматическое применение скачивает его, отказ отклоняет, а все остальное оставляет его ждать
пользователя. Из нерешенного предложения на диск не пишется ничего.

Передача тянет свои файлы по протоколу blob с типом полезной нагрузки `share.request` и ID
передачи предложения, поэтому прерванная передача продолжается с уже сохраненных чанков.
Отправитель обслуживает эти запросы, только пока держит передачу как offered, accepted или
transferring, что проверяет `transfer.ShareAuthorizer` сервиса отправки файлов.

| Лимит | Значение |
|-------|-------|
| Файлов на передачу | 32 |
| Передач в памяти | 64 |
| Ожидающих предложений | 16, по 8 на пира |
| Время жизни ожидающего предложения | 10 минут |
| Длина имени файла | 200 байт |

Полученные файлы пишутся в `share.downloads_dir` или по умолчанию в `~/Downloads/Unison`, под
безопасным именем со счетчиком, если имя занято. Платформа, которая держит файлы в другом месте,
передает `Sink` - так Android отдает их системному хранилищу.

## Загрузка

`core/download` готовит входящий файл: имя, безопасное на каждой платформе, новый файл, который
никогда не заменяет существующий, и отметку, которую платформа ставит на скачанные файлы, чтобы
система предупредила перед его запуском.

## Модель

`core/model` держит типы доменов, общие для пакетов: ID устройств, роли, платформы, виды
элементов, состояния сети и элемент clip. `core/model/protoconv` отображает их в protobuf
сообщения `proto/unison/wire/v1` и обратно, поэтому домен никогда не импортирует сгенерированный
код для типа, которым владеет сам.

## Порты

`core/ports` определяет интерфейсы, через которые ядро достает до операционной системы:

| Интерфейс | Ответственность |
|-----------|----------------|
| `Keystore` | загрузить, сохранить и удалить небольшой секрет по имени |
| `Clipboard` | следить за локальным буфером обмена и заменять его содержимое |
| `Discovery` | объявлять и искать сервис в локальной сети |
| `Clock` | источник времени, чтобы тесты управляли временем |

Пакет платформы возвращает `ErrUnsupported`, когда его сборка не может дать порт, например
хранилище ключей macOS, собранное без cgo, и демон не стартует с портом, который ему нужен.
`ports.SystemClock` - настоящие часы, а `core/ports/fake` реализует порты для тестов.
