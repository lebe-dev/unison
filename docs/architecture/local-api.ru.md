# Демон и локальный API

Русский | [English](local-api.md)

Демон - это процесс, который владеет устройством. Он запускает узел ядра, отдает локальный API на
эндпоинте своего каталога данных и работает, пока работает пользователь. Десктопное приложение и
клиент командной строки - его клиенты; на Android ядро работает в процессе приложения, и демона
там нет.

## Модель процесса

```
cmd/unisond
  internal/daemon.Run        data directory, lock, log, node lifecycle, endpoint
    core/node                the device
    core/api + localconn     the local API
  signal: SIGINT, SIGTERM    stop the API, stop the node, remove the endpoint
```

`internal/daemon` готовит каталог данных, берет блокировку единственного экземпляра, открывает
файл лога, поднимает хранилище ключей и имя устройства, создает узел с портами платформы, отдает
API и завершает все в обратном порядке.

Каталогом данных владеет один экземпляр. Демон берет исключительную блокировку на `unisond.lock`
и дополнительно проверяет, отвечает ли кто-то на эндпоинте; второй экземпляр сообщает, что уже
работает другой, и выходит с кодом 1. Система снимает блокировку при завершении процесса, поэтому
падение не оставляет за собой блокировку, а файл эндпоинта, который никто не обслуживает,
удаляется при старте.

## Команда

```
unisond [flags]

  -version            print the version and exit
  -data-dir path      data directory of this instance
  -endpoint path      local API endpoint of this instance
  -clipboard mode     system, auto, x11, wayland или none на Linux, system или none на остальных
  -name name          device name announced to peers
  -log-level level    debug, info, warn or error
  -log-stderr         copy the log to stderr
```

`--clipboard=none` запускает демон без системного буфера обмена - это нужно второму демону на
одной машине: иначе два демона читали бы и писали один и тот же pasteboard. На Linux `--clipboard`
выбирает бэкенд сеанса, см. раздел [Сеанс Linux](#сеанс-linux). Каталог данных по умолчанию
держит свои ключи в сервисе Keychain `app.unison`, а любой другой каталог данных - в
сервисе, названном по каталогу, поэтому два экземпляра на одной машине - это два устройства, и их
можно спарить.

`--name` задает имя устройства, которое объявляется пирам; если флага нет, используется имя,
сохраненное через локальный API, а без того и другого демон берет имя хоста без суффикса
`.local`.

## Каталог данных

| Путь | Содержимое |
|------|---------|
| `unison.db` | база SQLite, зашифрованная |
| `blobs/` | blob-хранилище |
| `logs/unisond.log` | лог JSON, пять MiB на файл, три ротированных файла хранятся |
| `unisond.lock` | блокировка единственного экземпляра |
| `unisond.sock` | эндпоинт локального API на платформах с unix-сокетами |
| `keys/` | файлы хранилища ключей на Windows и Linux |

Каталог по умолчанию - `~/Library/Application Support/Unison` на macOS, `%LOCALAPPDATA%\Unison` на
Windows и `$XDG_DATA_HOME/unison` (по умолчанию `~/.local/share/unison`) на Linux. `--data-dir`
дает экземпляру собственный каталог, и эндпоинт следует за каталогом: `unisond.sock` внутри него на
macOS и Linux, named pipe, производный от пути, на Windows.

Лог называет элемент буфера обмена по идентификатору, виду, размеру и MIME-типам, но никогда по
содержимому, и никогда не несет ключей или токенов. Пир, который вышел онлайн, логируется с
согласованными версией TLS и обменом ключами, поэтому соединение, которое откатилось к слабому
обмену ключами, видно.

## Сеанс Linux

Демон работает от имени пользователя и стартует вместе с графическим сеансом из пользовательского
юнита `packaging/linux/systemd/unisond.service`; пакет ставит его как
`/usr/lib/systemd/user/unisond.service`. Из репозитория юнит копируют в `~/.config/systemd/user/` и
включают:

```sh
systemctl --user daemon-reload
systemctl --user enable --now unisond
journalctl --user -u unisond -f
```

Юнит запускает демон вместе с сеансом, отправляет его стандартный вывод ошибок в journal и
перезапускает после сбоя; свой файл лога демон по-прежнему пишет в каталог данных. Менеджеру
пользователя нужны переменные сеанса: `systemctl --user show-environment` их печатает, а
`systemctl --user import-environment DISPLAY WAYLAND_DISPLAY DBUS_SESSION_BUS_ADDRESS XDG_RUNTIME_DIR`
добавляет их из оболочки сеанса. Если `DISPLAY` нет, демон работает в ручном режиме, пока его не
перезапустят с этой переменной.

### Буфер обмена

`--clipboard` выбирает бэкенд:

| Режим | Бэкенд |
|-------|--------|
| `system`, `auto` | бэкенд сеанса |
| `x11` | выделение CLIPBOARD протокола X11, доступное в сеансе Wayland через XWayland |
| `wayland` | протокол Wayland data-control, который предлагают KDE Plasma, wlroots и COSMIC |
| `none` | без системного буфера обмена, для второго демона на одной машине |

`auto` берет бэкенд Wayland data-control, когда сеанс его предлагает, и откатывается на X11 через
XWayland, когда нет - так на GNOME. Без дисплея демон продолжает работать в ручном режиме: пиры,
файлы, история и `unison send` работают, буфер обмена не синхронизируется, а причину называет одна
строка warn. Демон снова тянется к дисплею с паузой, которая удваивается до двух минут и дальше
составляет минуту, поэтому дисплей, появившийся после старта демона, подхватывается без рестарта.

Статус отдает бэкенд в `clipboard_backend` (`x11`, `wayland` или `none`), а причину ручного режима -
в `clipboard_note`; значения macOS и Windows - `pasteboard` и `win32`.

### Хранилище ключей

Демон держит идентичность и ключ шифрования данных в Secret Service сеанса, когда он есть, и в
файлах с правами 0600, когда нет. Бэкенд фиксируется первым секретом и отдается как
`keystore_backend` (`secret-service` или `file`, `keychain` на macOS, `dpapi` на Windows).
`unison status` печатает предупреждение, пока секреты лежат в файлах.

### Загрузки

Принятые файлы попадают в `Unison` внутри папки загрузок сеанса: папки `XDG_DOWNLOAD_DIR` из
`~/.config/user-dirs.dirs`, у которой на русской Ubuntu локализованное имя вроде `Загрузки`, или
`~/Downloads`, если файл ее не называет.

### Межсетевой экран

По умолчанию на Ubuntu межсетевой экран не включен, поэтому устройства локальной сети находят друг
друга без правила. Если `ufw` включен, разрешите mDNS и UDP-порт демона:

```sh
sudo ufw allow 5353/udp
sudo ufw allow <порт>/udp
```

`unison status` печатает порт в строке `address`. Он не случайный при каждом старте: первый старт
выбирает свободный порт и хранит его в настройках, поэтому одно правило действительно, пока
существует каталог данных. Окно спаривания слушает временный порт, который объявляется по mDNS,
поэтому спаривание с другим устройством требует и его; разрешение UDP из локальной подсети
покрывает основной порт, порт спаривания и mDNS одним правилом.

## Эндпоинт

`core/api/localconn` отдает API на эндпоинте. Эндпоинт говорит на HTTP/2 открытым текстом,
поэтому сертификат не участвует, а `http://unison` - только базовый URL сгенерированных клиентов.

| Платформа | Эндпоинт |
|----------|----------|
| macOS, Linux | unix-сокет `<data dir>/unisond.sock` |
| Windows, каталог по умолчанию | named pipe `\\.\pipe\unison-<user-sid>` |
| Windows, свой каталог | named pipe `\\.\pipe\unisond-<hash>` |

`UNISON_LOCAL_API` переопределяет эндпоинт, поэтому второй демон может работать рядом с
установленным.

На unix-сокете каталог создается с режимом 0700, а сокет - с 0600. Клиент отказывается от сокета,
который принадлежит другому пользователю или доступен другим пользователям, а также от каталога,
в который другие пользователи могут писать, поэтому эндпоинт нельзя подменить. Дескриптор named
pipe дает доступ только текущему пользователю.

| Лимит | Значение |
|-------|-------|
| Соединений одновременно | 16 |
| Таймаут простоя | 5 минут |
| Заголовок запроса | 64 KiB |
| Тело запроса и ответа | 1 MiB |

## Сервис

`core/api` реализует `UnisonService` из `proto/unison/local/v1`. Сервис принимает узел, версию
демона, имя устройства и необязательный `LocalClip`; без него `SetClip` сообщает, что вызов не
реализован, а демон передает конвейер буфера обмена узла.

| Группа | Методы |
|-------|---------|
| Статус | `GetStatus`, `WatchEvents` |
| Устройства | `ListDevices`, `RenameDevice`, `RevokeDevice`, `SetDeviceConfirmation`, `SetDeviceRemoteSettings`, `SetPeerAddress`, `RetryDevice` |
| Спаривание | `OpenPairingWindow`, `ExtendPairingWindow`, `ClosePairingWindow`, `ListPairingCandidates`, `StartSas`, `ConfirmSas`, `RejectSas` |
| Спаривание по QR | `GetPairingQr`, `ScanPairingQr` |
| Знакомства | `StartMediatedPair`, `ConfirmMediatedPair`, `RejectMediatedPair`, `CancelMediatedPair`, `ListMediatedPairs` |
| Буфер обмена | `GetClip`, `SetClip` |
| История | `ListHistory`, `GetHistoryItem`, `GetHistoryThumbnail`, `DeleteHistoryItem`, `ClearHistory`, `FetchHistoryItem`, `CopyHistoryItem`, `ApplyHistoryItem` |
| Передачи | `SendFiles`, `ListTransfers`, `CancelTransfer`, `AcceptTransfer`, `RejectTransfer` |
| Запросы | `SetFriendsDiscovery`, `ListRequests`, `DecideRequest` |
| Пауза | `GetPause`, `SetPause` |
| Настройки | `GetSettings`, `UpdateSettings`, `ExportSettings`, `ImportSettings` |
| Ретранслятор | `GetRelay`, `SetRelay`, `RelayOff`, `TestRelay` |

`WatchEvents` несет события шины узла: пир, который вышел онлайн или ушел офлайн, элемент буфера
обмена, пир, которому нужно обновиться, и события спаривания с адресом кандидата и коротким
кодом. События знакомства несут снимок знакомства через доверенное устройство. Ответ серверного
потока приходит с первым событием, поэтому клиент открывает поток до того, как ему понадобятся
события.

Статус, устройство и ретранслятор несут версию протокола, которую объявила другая сторона. События и
список устройств также сообщают, новее ли другая сторона, поэтому клиент может сказать пользователю
обновиться, а не только показать номер версии.

ID устройств - шестнадцатеричные в нижнем регистре, время - unix-миллисекунды. `GetClip`
возвращает последний элемент буфера обмена. Настройки держат имя устройства, флаги подтверждения
локального устройства, лимит blob-хранилища, каталог загрузок, время жизни и сетевую политику;
изменение применяется сразу. `ExportSettings` пишет их документом JSON, а `ImportSettings`
применяет такой документ ключами, которые в нем есть, и оставляет записанные значения для
остальных; см. [Файл настроек](settings-file.ru.md). Настройки ретранслятора отдаются как URL,
время изменения и признак того, сохранен ли токен, но никогда как сам токен. Статус называет бэкенд буфера обмена и причину
ручного режима, а также бэкенд хранилища ключей; см. раздел [Сеанс Linux](#сеанс-linux).

Десктопное приложение не работает с сокетом напрямую: его оболочка на Rust проксирует тот же API
из webview по Tauri IPC к эндпоинту. См. [Десктопное приложение](desktop.ru.md#прокси-локального-api).

## Ошибки

Ошибки ядра отображаются в коды connect:

| Условие | Код |
|-----------|------|
| нет пира, элемента или передачи | `not_found` |
| закрытое окно, остановленный узел, предложение не в ожидании | `failed_precondition` |
| устройство уже спарено | `already_exists` |
| отказанное устройство, отозванный пир, плохой токен | `permission_denied` |
| неверный ввод, искаженный запрос | `invalid_argument` |
| слишком много обменов спаривания | `resource_exhausted` |
| офлайн-пир, нет источника для полезной нагрузки | `unavailable` |
| неподдерживаемая операция платформы | `unimplemented` |
| все неожиданное | `internal` |

Внутренняя ошибка уходит в репортер ошибок, ошибка клиента - нет. Сообщение причины сохраняется;
оно никогда не несет содержимое буфера обмена или секреты.

## Клиент командной строки

`cmd/unison` говорит на том же API, поэтому ядром можно управлять без десктопного приложения. Он
попадает в `bin/unison` и достает до демона приложения без всяких опций, потому что оба
используют один эндпоинт.

```
usage: unison [--endpoint path] [--json] <command> [arguments]
```

| Команда | Назначение |
|---------|---------|
| `status` | демон, сеть, адрес и пиры |
| `devices` | список, адрес, переименование, подтверждение и отзыв |
| `pair` | открыть окно, перечислить открытые устройства, подтвердить код или присоединиться с `--qr` |
| `clip` | `get` печатает последний элемент, `set` копирует стандартный ввод в буфер обмена |
| `history` | список, загрузка и копирование записанных элементов |
| `send` | предложить файл или стандартный ввод устройствам из `--to` |
| `pause` | поставить на паузу или возобновить синхронизацию буфера обмена |
| `settings` | напечатать и изменить настройки, включая время жизни |
| `policy` | напечатать сетевую политику |
| `relay` | напечатать, задать и выключить доступ к ретранслятору |
| `friends` | запустить и остановить поиск устройств Friends |
| `requests` | перечислить предложения, ожидающие решения |
| `transfers` | перечислить передачи и отменить одну |

Устройство адресуется уникальным префиксом отпечатка, префиксом ID устройства или именем. Вывод
по умолчанию - простой текст, а с `--json` - JSON-форма сообщений API. Команда выходит с 0 при
успехе, 1 при сбое и 2, когда не может достать до демона.

## Отчеты об ошибках

`internal/observability` оборачивает Sentry. DSN и окружение задаются при сборке; отчеты выключены,
пока пользователь не даст согласие, которое хранится в настройке `sentry.enabled`. События несут
только стек, релиз, окружение и тег компонента: extras, breadcrumbs и данные запроса
отбрасываются, а абсолютные пути заменяются на `[path]` до того, как событие покинет процесс.
