# Clipboard and history

[Русский](clipboard.ru.md) | English

## What is shared

Text with its HTML flavour, images and files. Text and images are applied to the clipboard of the
receiving device, so a copy on one device is a copy on all of them; files are saved to its
downloads folder. Both apps show what arrived in their history.

How an item leaves a device:

- **macOS** - the daemon watches the clipboard of the session. A copy is announced to the online
  Personal devices about a quarter of a second after it happened.
- **Linux** - the daemon watches the clipboard of the session: through the data-control protocol on
  KDE Plasma, Sway, Hyprland and other wlroots desktops, and through X11 everywhere else. On GNOME
  Wayland the desktop keeps one clipboard for native windows and for XWayland, so the X11 path
  works there as well. Without a display, or with `--clipboard=none`, the daemon runs in the manual
  mode described below.
- **Android** - the system does not let an app watch the clipboard in the background, so the phone
  sends when you ask: the quick settings tile `Send clipboard`, the `Send clipboard` action of the
  notification, the button on the main screen, or `Share` in another app. Incoming text and images
  are still written to its clipboard without asking.

What arrives from the other devices is decided on the device that receives; see
[Network policies](policy.md).

An item that Unison itself put into the clipboard is not announced again.

## Linux specifics

Only the `CLIPBOARD` selection is synchronized; the `PRIMARY` selection, which a text selection
fills in X11, is left alone.

A password manager on Linux marks a copied password with the target `x-kde-passwordManagerHint`.
Such content is not sent and is not recorded in the history.

Content written by the daemon lives in its memory. When the daemon stops, the `CLIPBOARD` selection
has no owner any more, so the content disappears unless a clipboard manager of the desktop kept a
copy.

The daemon starts even when there is no display yet, which is what happens when the user unit runs
before the GNOME session is ready. It works in the manual mode: the paired devices, the file
transfers and the history work, but nothing is captured and incoming items are only recorded. The
daemon tries the display again with a growing delay, up to once a minute, and switches to automatic
without a restart. `unison status` shows the mode in `clipboard` and the reason in `note`:

## Advertising parameters

Links in text items lose the known advertising and campaign parameters before the item is stored
and announced, and again before an incoming item is written to the clipboard. That covers `utm_*`,
`gclid`, `fbclid`, `msclkid`, `yclid`, `igshid`, `twclid` and similar names of Google, Meta, X,
TikTok, Yandex and mail campaigns. The other parameters keep their order and encoding, as does the
text around a link.

The setting is on by default. Turn it off in `Settings` of the desktop app or in
`Settings > Clipboard` of the Android app;
`unison settings` shows it as `ad params`.

## Sensitive content

Content that the system marks as sensitive is never sent. That covers the markers of password
managers and of macOS (`org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType`,
`org.nspasteboard.AutoGeneratedType`) and, on Android, a clipboard that is marked as sensitive.

## Pausing

The clipboard synchronization can be paused for a while or until it is turned on again:

```sh
unison pause            # print the state
unison pause 5m
unison pause 1h
unison pause on         # until it is turned off
unison pause off
```

The tray menu of the macOS app and the second quick settings tile on Android offer the same. While
the clipboard is paused, nothing is captured or announced, and an item that arrives from another
device is dropped without being recorded.

## Images and files

Images are sent as PNG; a screenshot keeps its original format as a second flavour when it is small
enough. Images above 24 megapixels, 8192 pixels on a side or 64 MiB are skipped.

A file is announced as its name, size and hash. Copying files in Finder puts them into the
clipboard of the Mac as file references, which is how they travel. A received file lands in the
downloads folder:

| Platform | Folder |
|----------|--------|
| macOS | `~/Downloads/Unison` |
| Linux | `~/Downloads/Unison`, or the folder of `XDG_DOWNLOAD_DIR` |
| Android | `Download/Unison` |

On Linux the folder comes from `~/.config/user-dirs.dirs`, so a localized `Загрузки` is used when
the session has one; `unison settings` shows the result.

On the Mac the folder can be changed in Settings under "Received files". "Use default folder"
brings back `~/Downloads/Unison`. The new folder applies to the files that arrive afterwards;
files already received stay where they are. The command line client shows the current folder
with `unison settings`.

On Android the folder is chosen in `Settings > Files` under "Received files". The system folder picker
opens and Unison gets access to the folder you pick and to nothing else; the app asks for no
storage permission. If the access is lost, for example because the folder was deleted, files go
to `Download/Unison` again.

Files are fetched in verified chunks, so an interrupted transfer resumes where it stopped. Every
received file is checked against the hash of the announcement.

## Cache and size

An item up to 64 KiB travels inside the announcement. Anything bigger is stored in a local cache
and fetched by the other devices when they need it. The cache keeps at most 2 GiB and drops the
payloads that were used longest ago; a payload larger than the cache is refused, so a file above
2 GiB cannot be sent or received.

The cached payloads and the database live in `~/Library/Application Support/Unison` on macOS and in
the private directory of the app on Android.

## History

Every item that a device captures or receives is recorded in its history, with the device it came
from, the time, the type and the size. The history is shared with the Personal devices: a device
that was away catches up when it connects again, older items first. A large gap is filled over the
following connections.

An item lives for a fixed time from the moment it was captured:

| Type | Lifetime |
|------|----------|
| text | 7 days |
| images | 3 days |
| files | 24 hours |

Expired items are removed every ten minutes and when the daemon starts. Deleting an item removes it
on the other Personal devices as well, so it does not come back from them.

The lifetimes are a setting of the device that captured the item: it writes the expiry into the
item, so a change applies to the next copy and the items that are already recorded keep theirs. The
lifetimes are never sent to the other devices. Change them in `Settings` of the desktop app, in
`Settings > History` of the Android app, or from the command line:

```sh
unison settings                  # print the settings, with the lifetimes
unison settings ttl text 30d     # keep text for 30 days
unison settings ttl reset        # back to the defaults
```

Days and hours are accepted, from one second up to 365 days.

An item that arrived as metadata only is listed as not downloaded yet; the payload is fetched when
you ask for it, which needs the device that has it to be online.

Ways to work with the history:

- the History screen of the apps, with filters by type and by device, copy, download and delete;
- the Dashboard of the desktop app, which shows the newest items of every kind in three tabs and
  opens a preview of an item;
- clearing the whole history from the History screen of the macOS and Android apps, after a
  confirmation; the items are removed on the other Personal devices as well;
- `unison history`, `unison history fetch` and `unison clip get --from`, see
  [Command line](cli.md).

Copying an item from the history writes it to the clipboard of this device and does not announce it
to the others again.

## Dashboard

The Dashboard is the first screen of the desktop app. It shows the newest images, files and text as
three tabs. The number of items per tab is set in Settings and is 12 by default. A click opens the
item: the image in full size, the text with a copy button, or the files with copy and download.

On macOS an image or a file can be dragged out of the window into another app: Finder saves the
copies, a chat app attaches them, and a terminal inserts the path of a copy. Several files of one item
are dragged together. The copies live in the cache of the app and are removed a day after they were
written, so a terminal still reads them later. Text items are not dragged out; copy them with the
button of the preview.

A right click on an item opens its actions: `Send` offers the content to one online device as a file,
`Copy` puts it on the clipboard of this device without sending it anywhere, and `Delete` removes it
from this device and from the other Personal devices after a confirmation. `Copy` of an image or a
file copies the files themselves, so they can be pasted into Finder or an attachment field.

## Holding items until you apply them

A device that asks before it applies the clipboard of another device does not apply its items. They
are recorded in the history and marked as waiting for you, and the app asks at once: a small window
on macOS, a notification and a dialog on Android. The item is written to the clipboard when you
press `Apply` there or in the history, and only then. `Skip` leaves it in the history.

The flags are described under [Devices and pairing](devices.md#confirmation-flags).
