# Ретранслятор

Русский | [English](relay.md)

Ретранслятор соединяет устройства, которые находятся в разных локальных сетях. Он пересылает
непрозрачные датаграммы между участниками одного почтового ящика, поэтому устройства по-прежнему
используют обычное QUIC-соединение с взаимным TLS и постквантовым обменом ключами внутри него.
Ретранслятор не видит ни ключей, ни открытого текста, не узнает личность устройства и ничего не
хранит на диске.

Ретранслятор необязателен, и вы разворачиваете его сами: запустите его на сервере с публичным
адресом, и устройства одной личной группы будут им пользоваться. Клиент входит в состав демона и
мобильного ядра, сервер - это `unison-relay` из этого репозитория.

## Настройки

Доступ к ретранслятору принадлежит личной группе: адрес и один токен доступа. Оба значения хранятся
зашифрованными и передаются другим личным устройствам вместе с данными группы, поэтому все
устройства группы используют один ретранслятор.

Адрес - это хост и порт, с необязательной схемой `https://` или `wss://`. Порт по умолчанию 443,
путь, строка запроса, пользователь и фрагмент в адресе не допускаются:

    relay.example.com:443
    https://relay.example.com

Токен - секрет: демон хранит его, никогда не пишет в журнал и не возвращает. Клиенты узнают только,
сохранен ли токен.

```sh
unison relay                                          # адрес, токен, состояние, правило для файлов
unison relay set relay.example.com:443 --token <token>
unison relay off
```

`unison relay` также показывает транспорт зарегистрированного соединения: QUIC или WebSocket. В
приложениях для macOS и Android те же настройки находятся в разделе ретранслятора. Отключение
ретранслятора очищает адрес и токен для всей группы. Раздел ретранслятора обновляет состояние
соединения в фоне; адрес, токен и правило для файлов остаются такими, как вы их ввели, до
сохранения или отключения ретранслятора.

### Проверка соединения

Клиент ретранслятора подключается, только когда он нужен какому-то устройству, поэтому состояние
«ожидание» само по себе не отличает рабочий ретранслятор от неисправного. Кнопка **Проверить
соединение** в разделе ретранслятора приложений для macOS и Android сразу пробует оба транспорта с
адресом и токеном из формы, еще до сохранения; пустое поле токена означает сохраненный токен.
Проверка регистрирует одноразовый почтовый ящик, отключается и ничего не сохраняет.

В результате по строке на транспорт: время подключения и регистрации или причина неудачи:

| Причина | Что проверить |
|---------|---------------|
| Имя хоста не найдено | Адрес, DNS |
| Нет ответа | Хост, файрвол; для QUIC - сеть или хост, отбрасывающие UDP |
| Соединение отклонено | На порту ничего не слушает |
| Сертификат | Сертификат не из публичного доверенного центра или не совпадает с хостом |
| Не ретранслятор | По адресу другой сервис или прокси не пробрасывает `/relay` |
| Перегружен или недоступен | Ретранслятор заполнен или перезапускается, либо прокси не получает от него ответа |
| Токен не принят | Токена нет в файле токенов ретранслятора |
| Квота | Токен исчерпал квоту трафика за окно |

Неудача QUIC при работающем WebSocket означает рабочий ретранслятор: устройства переходят на
WebSocket, он медленнее. Под каждой неудачей показана техническая ошибка.

## Файлы через ретранслятор

Файлы - особый случай: по умолчанию файл остается в истории и передается через ретранслятор только
при скачивании, поэтому большой файл сам по себе не займет канал ретранслятора. Переключатель для
файлов в разделе ретранслятора в приложениях и `unison relay set --files-on-request` меняют это
правило; `--files-on-request=false` разрешает файлы через ретранслятор. Это настройка каждого
устройства, а не группы.

Также действует лимит ретранслятора из сетевой политики: элемент размером больше 1 МиБ не
скачивается сразу через ретранслятор, каким бы ни было состояние сети. Файлы в любом случае
остаются в истории; см. [Сетевые политики](policy.md). Те же правила действуют для файла,
предложенного через `unison send`: через ретранслятор он ждет в `Requests`, пока вы его не примете.

## Когда используется ретранслятор

Локальная сеть всегда в приоритете:

1. Устройство пробует сохраненные адреса собеседника, включая введенный вручную, и адреса,
   которые сообщает обнаружение.
2. Если собеседник недоступен 3 секунды, а сетевая политика разрешает трафик через ретранслятор в
   текущей сети, устройство открывает путь через ретранслятор.
3. Пока собеседник доступен через ретранслятор, устройство продолжает пробовать локальные адреса.
4. Как только собеседник отвечает в локальной сети, новое соединение занимает его место, а путь
   через ретранслятор закрывается. Ретранслятор никогда не используется для собеседника,
   доступного напрямую.

Сетевая политика разрешает ретранслятор в сети без ограничений и в сети с оплатой по трафику, а в
роуминге и при включенной экономии трафика блокирует. Путь каждого собеседника виден в состоянии:
`lan` или `relay`.

Устройство сначала пробует QUIC. Если UDP не проходит за 3 секунды, оно переходит на WebSocket
поверх TLS по тому же адресу. Этот вариант остается для следующих подключений, пока сеть не
изменится, поэтому сеть, блокирующая UDP, не пробует QUIC при каждой попытке.

## Почтовые ящики

Оба устройства пары выводят один и тот же почтовый ящик из общего ключа рандеву и текущего дня UTC,
где `day` - число дней с начала эпохи Unix:

    mailbox = BLAKE3(rendezvous_key || uint64_be(day))[:16]

Устройства, сопряженные напрямую, согласуют ключ рандеву при сопряжении. Два личных устройства,
которые знают друг друга через группу, выводят его из токена доступа группы и обоих идентификаторов
устройств, поэтому по одним идентификаторам нельзя узнать почтовые ящики пары.

Идентификатор меняется каждый день и ничего не говорит о паре, поэтому ретранслятор не может
проследить за устройством между днями. За 30 минут до полуночи UTC устройство регистрирует также
почтовый ящик следующего дня и еще 30 минут после полуночи держит ящик предыдущего, чтобы пара
оставалась доступной при смене суток, даже если часы устройств немного расходятся. Ретранслятор этой
версии меняет почтовые ящики живого соединения; со старым ретранслятором клиент открывает новое
соединение с новым набором.

Почтовые ящики привязаны к токену доступа. Соединение входит в ящики только внутри пространства
имен своего токена, поэтому один и тот же ID ящика под двумя токенами - это два несвязанных ящика.
Устройства разных групп никогда не встречаются, даже если одному из них известен ID ящика другого.

## Что видит ретранслятор

Ретранслятор видит адреса клиентов, имя сервера в TLS и время подключений, токен, который
предъявляет соединение, идентификаторы почтовых ящиков, к которым оно присоединяется, а также размер
и частоту датаграмм. Он может определить, что два соединения в один день используют один почтовый
ящик и что устройства используют один токен.

Он не видит содержимого датаграмм, ключей, идентичностей устройств и связи между парой на разных
днях. Соединение одного токена не может войти в ящики другого токена или получать их трафик, поэтому
группа остается изолированной, даже если ее ID ящиков станут известны.
Внутреннее соединение сохраняет собственные TLS 1.3, гибридный обмен ключами, проверку сертификата
и подтверждение подлинности сеанса, поэтому ретранслятор - это транспорт, который видит только
шифротекст. См. [Безопасность](security.md).

## Запуск ретранслятора

Репозиторий собирает образ контейнера с сервером и небольшой программой проверки работоспособности.
Образ собирается с нуля: в нем нет оболочки и менеджера пакетов, процесс работает под uid 10001, а
корневая файловая система может оставаться доступной только для чтения.

```sh
just relay-image              # unison-relay:<version>
```

Compose-файл по умолчанию монтирует три файла из `deploy/relay/secrets`: `cert.pem`, `key.pem` и
`tokens.txt`. Затем запустите compose-файл или контейнер напрямую:

```sh
just relay-run
docker compose -f deploy/relay/docker-compose.yml up -d
```

Compose-файл и заметки для администратора находятся в `deploy/relay`.

| Порт | Протокол | Назначение |
|------|----------|------------|
| 443 | UDP | QUIC, основной транспорт |
| 443 | TCP | WebSocket поверх TLS, запасной вариант для сетей, блокирующих UDP, путь `/relay` |
| 8080 | TCP | `GET /healthz`, `GET /readyz` и `GET /metrics`, обычный HTTP, только loopback |

Устройства обращаются к ретранслятору по URL, например `https://relay.example.com`, и используют
один порт для обоих транспортов, чтобы клиент мог перейти с QUIC на WebSocket без смены адреса.

Один экземпляр может обслуживать группу: почтовые ящики хранятся в памяти, поэтому вторая копия
получит собственный набор ящиков, а поэтапный перезапуск разорвет соединения устройств.

### TLS

Ретранслятор сам завершает TLS, поэтому сертификат и ключ монтируются в контейнер. Рекомендуется
сертификат от публичного удостоверяющего центра. Файлы должны быть доступны для чтения uid 10001.
Ретранслятор не запрашивает клиентские сертификаты: устройства проверяют друг друга внутри
зашифрованных датаграмм.

### Токены доступа

У каждой группы один токен, и сервер хранит в памяти только его SHA-256:

```sh
openssl rand -hex 32 > deploy/relay/secrets/tokens.txt
chmod 0444 deploy/relay/secrets/tokens.txt
```

В файле по одному токену на строку; пустые строки и строки, начинающиеся с `#`, пропускаются.
`UNISON_RELAY_TOKENS` принимает вместо этого список через запятую, но тогда токены остаются в
окружении контейнера. Сервер читает токены при запуске, поэтому после изменения файла перезапустите
контейнер.

Один ретранслятор обслуживает столько групп, сколько токенов в файле. SHA-256 токена также задает
пространство имен его почтовых ящиков, поэтому группы делят сервер, но никогда не трафик друг друга.

Для токена действуют ограничения: 200 датаграмм в секунду со всплеском до 400 и 1 ГиБ трафика за
24 часа. Частота и квота относятся к токену, а не к одному соединению, поэтому все устройства группы
делят их. При превышении частоты ретранслятор отбрасывает датаграммы и сохраняет соединение; при
превышении квоты он закрывает соединение. Трафиком считаются только датаграммы, прошедшие проверки.

### Размер датаграммы

Датаграмма ретранслятора передается в одном пакете QUIC, поэтому ретранслятор ограничивает ее
полезную нагрузку (`max_datagram_bytes`). QUIC-соединение между устройствами работает внутри этих
датаграмм, а для рукопожатия QUIC нужны пакеты не меньше 1200 байт, то есть 1224 байта полезной
нагрузки ретранслятора после заголовков кадра.

Оставьте значение по умолчанию 1400 байт. Оно дает внутреннему соединению пакет 1216 байт и
отключает для него определение MTU пути. Значение больше 1240 байт не увеличивает внутренний пакет,
потому что в один пакет QUIC ретранслятора помещается не больше. Ретранслятор, настроенный на
значение меньше 1224 байт, не может провести рукопожатие, поэтому устройства отказываются от пути
через ретранслятор и пишут предупреждение в журнал.

### Размещение в сети

QUIC работает по UDP, и обычный HTTP-прокси или ingress не могут его маршрутизировать: они
принимают TCP и работают с путем запроса. Опубликуйте UDP-порт на хосте с ретранслятором или
поставьте перед ним балансировщик L4 либо правило межсетевого экрана, которое пересылает UDP и TCP
на один и тот же порт, не трогая пакеты. Запасной WebSocket - это обычный TLS поверх TCP, и он
проходит через ingress, в котором включено обновление до WebSocket. Ретранслятор отправляет ping в
простаивающий WebSocket каждые 30 секунд, поэтому тайм-аут простоя в ingress должен быть больше.

### За обратным прокси

Если UDP недоступен, ретранслятор можно запустить за прокси, который завершает TLS. Compose-файл
`deploy/relay/docker-compose.proxy.yml` публикует только порт WebSocket и порт проверок на loopback:

```sh
RELAY_IMAGE=unison-relay:<version> RELAY_WS_PORT=8443 \
    docker compose -f deploy/relay/docker-compose.proxy.yml up -d
```

Прокси пересылает `/relay` на `https://127.0.0.1:8443` с заголовками для обновления до WebSocket,
а устройства используют домен прокси без пути. Самоподписанного сертификата между прокси и
ретранслятором достаточно, потому что устройства доверяют сертификату прокси.

### Проверки и метрики

```sh
curl -s http://127.0.0.1:8080/healthz
curl -s http://127.0.0.1:8080/readyz
curl -s http://127.0.0.1:8080/metrics
```

`/healthz` сообщает, что процесс работает, `/readyz` - что он принимает соединения, а `/metrics`
отдает формат Prometheus: соединения, регистрации, активные почтовые ящики, датаграммы и байты по
транспортам, время работы и отброшенные датаграммы по причинам. В метках нет идентификаторов ящиков,
токенов и адресов.

### Настройки сервера

| Флаг | Переменная окружения | Значение по умолчанию |
|------|----------------------|-----------------------|
| `-quic-addr` | `UNISON_RELAY_QUIC_ADDR` | `:8443`, `:443` в образе |
| `-ws-addr` | `UNISON_RELAY_WS_ADDR` | `:8443`, `:443` в образе |
| `-http-addr` | `UNISON_RELAY_HTTP_ADDR` | `:8080` |
| `-tls-cert`, `-tls-key` | `UNISON_RELAY_TLS_CERT`, `UNISON_RELAY_TLS_KEY` | обязательны |
| `-tokens`, `-tokens-file` | `UNISON_RELAY_TOKENS`, `UNISON_RELAY_TOKENS_FILE` | нет |
| `-log-level` | `UNISON_RELAY_LOG_LEVEL` | `info` |
| `-max-datagram-bytes` | `UNISON_RELAY_MAX_DATAGRAM_BYTES` | 1400 |
| `-rate`, `-rate-burst` | `UNISON_RELAY_RATE`, `UNISON_RELAY_RATE_BURST` | 200 в секунду, всплеск 400 |
| `-quota-bytes`, `-quota-window` | `UNISON_RELAY_QUOTA_BYTES`, `UNISON_RELAY_QUOTA_WINDOW` | 1 ГиБ, 24 ч |
| `-max-mailboxes` | `UNISON_RELAY_MAX_MAILBOXES` | 32 на соединение |
| `-max-mailboxes-total` | `UNISON_RELAY_MAX_MAILBOXES_TOTAL` | 100000 |
| `-max-connections` | `UNISON_RELAY_MAX_CONNECTIONS` | 4096 |
| `-ping-interval` | `UNISON_RELAY_PING_INTERVAL` | 30 с |
| `-register-timeout` | `UNISON_RELAY_REGISTER_TIMEOUT` | 10 с |

Одно соединение обслуживает почтовые ящики всех пар, которые используют ретранслятор, - до двух
ящиков на пару незадолго до полуночи. Увеличьте `-max-mailboxes`, если много устройств группы
одновременно находятся вне локальной сети; максимальное значение - 256. Если устройству нужно больше
ящиков, чем разрешает ретранслятор, пары, открытые раньше, сохраняют свои, а устройство пишет в лог,
что остальные ждут свободного места.

Переменные окружения задают значения по умолчанию, флаги их переопределяют. Список флагов выводит:

```sh
docker run --rm unison-relay:<version> -h
```

## Переподключение

После сбоя клиент переподключается с экспоненциальной задержкой: 1 секунда, затем удвоение до 30
секунд, и снова регистрирует свои почтовые ящики. Когда пир начинает или перестает пользоваться
ретранслятором или в полночь UTC меняются ящики дня, клиент меняет почтовые ящики живого соединения,
поэтому сеансы с другими пирами через ретранслятор не прерываются. Ретранслятор старой версии так не
умеет: тогда клиент заменяет соединение - сразу при изменении набора ящиков и в полночь UTC для
нового дня.

Сеанс между двумя устройствами переживает сбой ретранслятора длительностью до 15 секунд: пакеты
передаются повторно, когда соединение с ретранслятором восстанавливается. Если ретранслятор
отсутствует дольше, сеанс завершается и открывается снова, когда ретранслятор возвращается.
